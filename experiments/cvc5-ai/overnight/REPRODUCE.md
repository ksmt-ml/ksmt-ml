# Ночная кампания cvc5 — воспроизведение на butvinm-work

Локальный корень `~/Dev/cvc5-ai-pilot/overnight`. Все создаваемые файлы находятся
в нём. `../campaign`, `../interactive`, архив старого клиента и установленные
JAR, JDK, Python, cvc5 и Z3 используются для чтения. Нужны сохранённые зависимости
сервера. Новые установки или загрузки не нужны. Модельная часть использует только
существующий вход Codex CLI, которому передаются обучающие данные в отдельном
пространстве монтирования.

## Порядок

```sh
cd ~/Dev/cvc5-ai-pilot/overnight
export OPENBLAS_NUM_THREADS=1 OMP_NUM_THREADS=1 MKL_NUM_THREADS=1
../campaign/.venv/bin/python -B corpus.py
../campaign/.venv/bin/python -B stabilize.py
../campaign/.venv/bin/python -B early.py
../campaign/.venv/bin/python -B transfer.py
../campaign/.venv/bin/python -B search.py smoke
../campaign/.venv/bin/python -B search.py full
../campaign/.venv/bin/python -B calibration.py
python3 -B report.py
```

Сценарий воспроизводит этапы кампании по порядку. Для повторного сбора
следует использовать новый каталог результата и отдельное предварительное
обязательство по seed. Исходные планы и измерения лежат в `protocols/` и
`runs/`. Сценарий `corpus.py` создаёт обязательства, а `release.json` в новом
корпусе сопоставляет опубликованный после фиксации seed с его хешем и
хешем файла с решениями. Тренировочная изоляция не монтирует `private/`,
валидацию, зафиксированные решения или какой-либо тест. Для пересчёта результатов
сеть и модель не нужны.

Для повторной проверки полного матричного журнала достаточно вызвать
`../campaign/.venv/bin/python -B replay.py verify runs/<этап>/<повтор>`.
(Для устойчивости: `runs/01-stability`.) Проверка восстанавливает все
перестановки, сверяет целостность файлов и проверяет ответы, штрафы и объём
по исходным оракулам. `metrics.json` хранит значения по программам, интервалы,
условия и seed анализа. `evidence/*.json` строятся из верифицированных метрик и
содержат подписи и таблицы. `python3 -B report.py` атомарно строит автономный
HTML и текущий статус. Запускать повторное построение отчёта во время записи
карточки необязательно.

## Границы измерения

- Сессия — один упорядоченный поток SMT-LIB от метода USVM, воспроизведённый
  из замороженной записи на новом процессе cvc5 1.4.1. Значение проверок сверяется
  с исходным Z3. Затребованные модели и ядра запрашиваются при повторе, их
  конкретное представление не сравнивается.
- PAR2 — прошедшее время полного корректного сеанса или удвоенный предел.
  Глобальные отсечения бюджета записываются отдельно. Исследовательские
  интервалы строятся по программам, семействам и/или seed настройки, как
  описано у каждой таблицы. Отдельные повторные тайминги не увеличивают число
  независимых программ.
- Порядок внутри блока «программа × повтор» заново перемешан. Все элементы
  блока проходят на одном физическом ядре. Суммарно доступно не более 6
  рабочих ядер. Предел диска с запасом для завершения процессов — 13,5 ГБ
  суммарного наблюдаемого объёма, срок запуска измерений — 10:48 МСК.
- Для повторов с библиотеками данные старого клиента используются для проверки
  происхождения и ограничений. Новые логи записывают полные упорядоченные
  сеансы. Архивные одиночные запросы — исторический контекст.
- Java-поиск путей ограничен по времени, поэтому повторная запись может
  изменить сами трассы. Для прямого сравнения флагов используйте сохранённые
  SMT-LIB из одной и той же записи.

Файлы отчёта `report.html`, `current.json`, `summary.txt` и `research.log`.

## Продолжение и исправленные попытки

Ночные контроллеры `pipeline.py`, `followups.py`, `later.py`,
`tail_campaign.py` и `after_tail.py` запускают серии по готовности
предшествующих данных. Фактический порядок и статусы находятся в
`research.log`, `protocols/phase-status.json` и протоколах восстановления.
Отсыпка времени через эти контроллеры не заменяет измерения.

Первичные манифесты библиотек и калибровки с ошибочной проверкой `close`
сохранены. Допущенные данные оттуда перенесены по исходным хешам записей
в `corpus-recovered/`; новый аудит Z3 находится рядом.
В исходном инструменте завершение метода записано отдельной строкой
драйвера. Эта строка и баланс push/pop определяют конец сеанса.
Сырые замеры, записанные после устранения ошибки запуска, не смешаны
с неудачными попытками.

Для необязательного языкового моста `bridge.py` сохраняет каждую
преобразованную SMT-LIB запись, список изменённых операций, отдельный
парсерный контроль и ответ Z3 для всей последовательности. Дополнительный
флаг и источник SMT-LIB указаны для каждого режима в плане.
`finish.py --full` независимо проверяет всё завершённое на момент вызова.
Ключ `--final` предназначен для конца ночного окна после остановки измерений.

## Дополнительные проверки переноса

- `arrays_options.py` записал другие проекты и воспроизвёл два флага
  массивов и разложение C05. После полного прогона отдельная сверка
  `real_selector.py` исключила один межпроектный сеанс, идентичный
  обучающему. Исходные показатели селектора сохранены рядом с исправленными.
  `array_error_probe.py` сохранил полный диагностический ответ fp.to_ieee_bv.
- `core_groups.py` использует два непересекающихся трёхъядерных пула.
  Сравнение групп и состояние SMT фиксируются в `protocols/core-classes.json`.
  `progress_probe.py` проверяет альтернативный порядок отбора из
  уже измеренных конфигураций, а `aligned_search.py` проводит новый
  замкнутый Sol/RF/SMAC с совместной шестипроцессной разминкой.
  Каждый новый закрытый набор выпускается после фиксации решений.
- `reset_batches.py`, `library_caps.py` и `rewrite_transfer.py` содержат
  проверки пакетного reset, лимитов 0,75/1,50/3,00 с и переноса
  зафиксированных флагов переписывания. Манифесты фиксируют хеши,
  зависимости и точные совпадения между наборами.
- `native_probe.py` запускает `NativeOptionsProbe.java` на штатном JNI.
  `native_overlay.py` компилирует локальный класс на основе исходной
  фабрики солвера. Только установленные им параметры и их фактическое
  значение меняются в эксперименте `native_variant.py`; загружаются те
  же зависимости KSMT и тот же клиент. Векторы и версии указаны в
  протоколах, а подтверждение загрузки класса записано в каждой JVM.
- `model_witness.py` проводит дополнительную проверку скалярных
  значений моделей. Сохранены участки SMT-LIB с исходной областью
  ограничений, дополненные равенствами значений, и отдельный вывод Z3.
- `matched_forecast.py original` и `matched_forecast.py aligned`
  сверяют принудительные варианты Sol и RF с фактическими оценками
  в обеих ветках. Это пересчёт на обучении. В `runs/20-aligned-incomplete/`
  сохранена прерванная попытка перед исправлением дискового контроля.
- `rewrite_profile.py`, `warm_load.py` и `simplification_probe.py`
  содержат проверку фаз ускорения, масштабирования двух и шести
  процессов и отделения одного параметра от группы переписывания.
- `budget_tradeoff.py` пересчитывает полное время попыток и долю
  завершения при разных лимитах, без сравнения разных штрафов PAR2.
  `paired_rewrite.py` расширяет опыт ветвления и таблицы новыми
  семействами. При коротком окне `--reuse` сохраняет исходные
  парные программы и меняет только сравниваемые параметры.
- `native_budget_repair.py` использует те же 36 методов, по три на
  JVM, с увеличением только внешнего ограничения процесса до 75 с
  и двумя измерениями на метод и режим. Обе серии сохраняются.
- `minimal_transfer.py` проверяет `simplification=none` на
  других библиотеках или на прежних записях при коротком окне.
  `library_synthesis.py` сверяет раздельные наборы 76 и 87 методов
  и даёт сводную оценку C05 при 1,5 с без дублирования потоков.
  `model_request_cost.py` сравнивает исходные полные потоки с
  диагностической версией, где удалены только команды get-model.
- `portable_solver_control.py`, `portable_solver_replicate.py` и
  `backend_cap_probe.py` запускают полный неизменённый SMT-LIB в
  CLI cvc5 и Z3. Запросы модели и ядра проходят с теми же утверждениями
  и проверками. Для каждого процесса сохранены stdout/stderr в gzip,
  статус, хеш входа и причисление к перемешанному блоку.

Контроллеры `aligned_after.py`, `reset_after.py`, `caps_after.py`,
`rewrite_after.py`, `native_after.py` и `witness_after.py` передают
измерительные ядра по атомарному маркеру предыдущей стадии. Протоколы
сохраняют предел ночи. Для нового сбора за её пределами используйте копию
кодовой части, новый абсолютный срок и отдельные каталоги результатов.
Проверка имеющихся данных и построение HTML новых измерений не запускают.
