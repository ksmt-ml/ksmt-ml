# 02. Почему fp.to_ieee_bv выпадает из живого эксперимента

Новый доброкачественный контракт использует числа IEEE 754 без входов из тестовых проектов. Проверяем знак нулей, конечные числа, минимум субнормали, бесконечности и канонизированный NaN в 32 и 64 битах. Для каждого случая возможное значение должно давать SAT, противоположность — UNSAT; у SAT сверяется значение модели. Проверяем отдельно (A) прямой KSMT вызов fp.to_ieee_bv для не-NaN, (B) обратное ограничение с отдельной переменной битов и равенством восстановленного FP исходному, а для NaN — канонический шаблон Java. Равенство термов FP применяется вместо fp.eq, чтобы сохранить различие знака нуля. У raw NaN не фиксируем произвольную полезную нагрузку. Базовый float-контракт, scope и native identity обязательны перед тестами.

Плечи cvc5 default, arrays-exp=true, bv-eager-eval=true, simplification=none, static-learning=false, Z3 с прежними настройками клиента, три независимых JVM-повтора каждого. Порядок по ядрам записывается до запуска. Сравнения исходов и моделей имеют приоритет перед временем. Ошибки кодирования, обычные UNKNOWN, таймауты и неправильные результаты подсчитываются отдельно. Ожидаемое различие между представлениями проверяет границу API на этих входах. Перекодирование в архив или USVM текущей серии не вносится. Стоп после 18 JVM или 8 минут и до общего дедлайна.
