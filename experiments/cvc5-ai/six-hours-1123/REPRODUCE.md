# Воспроизведение на butvinm-work

Рабочий каталог `six-hours-1123`. Время на хосте проверяется командой
`TZ=Europe/Moscow date -Is`. Окно сбора 23.11.2026 заканчивается до 09:21
МСК. Прочтите `CHECKPOINT.md` перед продолжением. Длительные исполнители
ниже переиспользуют завершённые блоки. Отчёты перегенерируются атомарно.
Все локальные зависимости используются из уже установленного рабочего
окружения. Корневые пути к историческим данным разрешены в изолированных
копиях скриптов. Исходные кампании нужны только для чтения.

## Восстановленный тест

```sh
export PYTHONDONTWRITEBYTECODE=1
taskset -c 12-15 ../.venv/bin/python recovery/scripts/diagnose.py
taskset -c 12-15 ../.venv/bin/python recovery/scripts/recover.py
taskset -c 12-15 ../.venv/bin/python recovery/scripts/summarize.py
../.venv/bin/python scripts/render.py
```

`recovery/inputs` содержит историческую предрегистрацию, точный манифест,
расписание, идентификаторы версий и замороженный выбор. В `recovery/raw`
отдельно хранятся полные архивные блоки, карантин, послеперезагрузочная
калибровка и динамический повтор. Агрегаты можно сверить в
`recovery/evidence/paired-cells.json` и `verified-sha256.json`. Поиск
сверяется по сырым копиям из `recovery/raw/selection`.

## Разрешение времени и проверка API

```sh
sha256sum -c followup/inputs/power.sha256
taskset -c 14 ../.venv/bin/python followup/src/prepare.py
taskset -c 14 ../.venv/bin/python followup/src/build.py
taskset -c 12-15 ../.venv/bin/python followup/src/run_power.py
taskset -c 12-15 ../.venv/bin/python followup/src/analyze_power.py
taskset -c 12-15 ../.venv/bin/python diagnostics/src/historical_errors.py
taskset -c 12-15 ../.venv/bin/python diagnostics/src/run_fp.py
```

Драйвер A/A строится отдельно от исходного. Просмотрите
`followup/evidence/power-preflight.log`, `power-summary.json`, сертификаты
JVM и исходные записи по каждому методу. FP-контракт и классификация
стеков записаны в `diagnostics/evidence`.

## Независимые нативные нагрузки и тёплый JVM

```sh
taskset -c 12-15 ../.venv/bin/python native/src/freeze.py
taskset -c 12-15 ../.venv/bin/python native/src/run.py
taskset -c 12-15 ../.venv/bin/python native/src/analyze.py
taskset -c 14 ../.venv/bin/python screening/src/freeze.py
taskset -c 14 ../.venv/bin/python screening/src/prepare.py
taskset -c 12-15 ../.venv/bin/python screening/src/screen.py
../.venv/bin/python scripts/render.py
```

Протоколы и критерии находятся в `protocols`. Нативные программы сохранены
в целочисленных SMT-LIB потоках с SHA-256 и отдельным известным оракулом
`native/inputs/manifest.json`. Распределение библиотек сохраняется отдельно
от train и тестовых динамических данных. Трасса USVM является
консервативной сверкой последовательности наблюдаемых операций. При
различиях в именовании или выборе пути возможно расхождение хешей у
логически эквивалентных выражений.

## Отчёты и ограничения

`report.html` и `recovery/report.html` читаются автономно, без сети.
Запуски закреплены за Linux CPU 12–15 из четырёх разных физических ядер.
Сырые временные отметки имеют смещение +03:00. Параметры отдельных
исполнителей зафиксированы в сырых `invocation.json` и `status.json`.
Для верификации можно повторно запускать анализ по существующим сырым
файлам. Сбор новых динамических данных допускается только в исходном
окне времени.

После ограничения памяти у длинных JVM-пакетов запущена компактная
предрегистрированная схема `screening/src/compact.py`. 08b использует
изолированную копию запуска 01 и новую дозу. Свежий контраст JVM и нативный
контракт воспроизводятся следующими командами.

```sh
taskset -c 12-15 ../.venv/bin/python oracle-live/src/run.py
taskset -c 12-15 ../.venv/bin/python bv-study/src/run.py
taskset -c 12-15 ../.venv/bin/python bv-study/src/analyze.py
taskset -c 12-15 ../.venv/bin/python stable/src/run.py
taskset -c 12-15 ../.venv/bin/python budget/src/run.py
../.venv/bin/python scripts/render.py
../.venv/bin/python scripts/verify_campaign.py
```

Условный поиск запускается по правилам протокола после соответствующего
допуска. Новые закрытые методы и измерения остаются в рабочих манифестах
и никогда не отображаются в каталоге входа для модели. Результаты
проверки режима входа и синтетического запроса лежат в `blind/evidence`.

Полные статистики шага, входа и операций пишутся отдельными цепочками
в `trace-cause`. Дополнительные протоколы можно запускать последовательно
через `scripts/stage.py trace`, затем `kernels`, `interactions`,
`budget`, `live-resource`, `fp-encoding`, `cpu-dose`, `order-trace`, `ast-shadow` и `panel`.
Это аргументы одного последовательного исполнителя. Эта оболочка автоматически задаёт affinity, пишет
журнал времени и обновляет HTML. При активном другом измерительном этапе
дождитесь его завершения на тех же физических ядрах.

Решения `cold-search` и `native-search` оболочка запускает отдельным
интерпретатором `../campaign/.venv/bin/python` с SMAC 2.4.0 и
ConfigSpace 1.2.1. Внутренние предрегистрационные проверки допуска
сохраняются в evidence, даже когда набор не допускает новый поиск.

`order-trace` дополнительно хеширует мультимножества исходных выражений.
Измерение полной упорядоченной цепочки и её точного общего префикса
сохраняет обычные границы сопоставления. Патчи KSMT-входа и FP-кодирования
компилируются в отдельных каталогах. Операции сортировки и конкретные
проверки Java доступны в сырых результатах.

В `ast-shadow` один экземпляр управляющего cvc5 запускает USVM. Отдельные
решатели получают те же типизированные объекты уже после сбора префикса.
Файл `shadow.tsv` сверяет порядок, размеры, опции, JNI версию, исходы,
ошибки и времена ответов. Сама траектория управляется заводским cvc5.
`ast-shadow/src/analyze.py` восстанавливает причинные метки UNKNOWN и
разбивку совпавших ответов по наблюдаемым теориям из закрытых локальных логов.

`array-semantics` воспроизводит независимый эксперимент с константными
массивами и проверяет устранение STORE_ALL. Исчерпывающий Java оракул и
контракты настроек сохранены в его `evidence`.

`array-search` проверяет отдельный допуск 20 и при успехе запускает
equal-budget раунды Sol, SMAC и random на живых Java методах из
`array-tuning`. Динамический тест требует наличия `evidence/test-lock.json`
и всегда включает заводскую конфигурацию и одиночную `arrays-exp=true`.
`array-transfer` проверяет настройку без нового поиска на методах свежих
библиотек, отобранных по операциям над массивами в байткоде. `width`
воспроизводит зависимость BV переключателя от разрядности и таймаута.
`prompt-study` использует только сохранённые первые train пакеты раундов
Sol и фактические значения трёх default из тех же train JVM. Этот этап
сохраняет новый диагностический запрос, исходные измерения остаются целы.
Для расчёта мощности и дозы по завершённым библиотечным данным запустите
`library-panel/src/precision.py` с тем же интерпретатором.
`smac-recovery` использует зафиксированное до закрытого теста правило 23
и исходный контроль A/B только для неспособного начать оценки третьего
SMAC. Исправление сохраняет запреты ConfigSpace при первоначальной выборке.

`resource-calibration` выполняет только первую фазу 15. Полная команда
`live-resource` при необходимости использует тот же запечатанный выбор и
сверяет уже записанные калибровочные блоки.
`pure-resource` проверяет эффект аварийного `tlimit-per` на выбранной
диагностической части запечатанных нативных программ 07.
`logic-study` сравнивает то же тело SMT-LIB при исходной декларации и ALL.
`logic-complement` повторяет сравнение на остальных подтверждённых Z3 потоках.
`logic-unused-uf` добавляет промежуточное объявление, включающее UF, на
первых восьми потоках. Тела формул в сравниваемых вариантах побайтно равны.
`logic-unused-uf/src/analyze.py` анализирует тот же набор совместно
правильных ответов во всех плечах и даёт чувствительность к весу семейств.
`resource-live-mini` использует малый запечатанный живой префикс для
проверки одного воспроизводимого ресурсного лимита.
`resource-live-hi` применяет более высокий предел на том же коротком блоке
с отдельными JVM и результатами. `trace-overhead` измеряет влияние записи
SHA цепочки. `closing-calibration` проверяет тот же SHA контроль в конце окна.

После закрытия окна `scripts/close.py` сверяет, что рабочая блокировка
свободна и последние записанные измерения завершились до 09:21 МСК.
Скрипт атомарно завершает статус и обновляет отчёты. Независимая сверка
в любое время использует `scripts/verify_campaign.py --full`.
