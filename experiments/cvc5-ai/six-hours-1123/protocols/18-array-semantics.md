# 18. Константные массивы, STORE_ALL и достижимые исходы в живом USVM

В 11 четыре программы Overwrite дали 16 неполных наблюдений на каждое плечо. По одному default JVM на repeat, в каждом из четырёх методов ответы UNKNOWN объяснялись невозможностью обработать STORE_ALL. Этот опыт проверяет причинный механизм. Создаём шесть отдельных семейств Java классов по четыре программы. Пять семейств используют штатные индексированные записи в локальные массивы с пустым, разреженным или заполненным начальным состоянием. Шестое выполняет скалярную операцию без массива. Каждая программа заранее ограничивает входы и проверяется исчерпывающим перебором на штатном JVM.

Плечи A/B default cvc5, E arrays-exp=true, EI arrays-exp=true вместе с arrays-eager-index=false, ES arrays-exp=true вместе со static-learning=false и Z3 4.13.0.0. Каждый вектор cvc5 сначала проверяется нативно до и после check. Измерение на четыре независимых ядра, четыре JVM-повтора, по два c одинаковым seed 0 и 71, одна воспроизводимая случайная ротация каждого блока. Предел 3000 шагов без ограничения времени анализа, 1,6 с на вызов solver, внешний ограничитель JVM. Конкретный свидетель исполняется независимым вызовом Java и проверяется каждый достижимый исход.

Первичный диагноз — воспроизводимый STORE_ALL в A/B на новых задачах, исчезновение причины UNKNOWN и восстановление ожидаемых классов при E. Скалярный контроль проверяет специфичность. Критерий поддержки E — правильные свидетели, рост доли полных независимых программ в затронутом семействе, отсутствие потери полноты в других семействах. Вторично фиксируем полный PAR2 и издержки относительно default и E. Для вывода об ускорении сравниваем только методы с совпавшими рабочими счётчиками и полным Java оракулом. Практический перенос требует отдельного проекта. Этот опыт не допускает новый поиск сверх E без подтверждённой экономии на сопоставимой работе. Сбор останавливается по расписанию или общему дедлайну.
