# Live USVM — preregistration v1

Locked before any new solver run or measured holdout execution. Linux host butvinm-work.
Question: does cvc5 1.4.1 with only simplification=none improve end-to-end live USVM vs same pinned 1.4.1 defaults, and how do both compare with default native Z3?

## Arms and engineering gate

Preferred three arms in the same JVM mode, on the installed USVM commit 814a963 with the prior client instrumentation. Keep KSMT 0.5.26 core and Z3. Recompile only the 0.5.26 cvc5 adapter against the official 1.4.1 Java/JNI release. Exclude old cvc5 jars from the runtime classpath. Start with the published compatibility shim and change APIs only as required. Keep shared integration defaults from the adapter (e.g. models and cores); no TableIte, SMT dump, or replay. Option arm overrides only simplification. Hash release artifacts and mapped libraries, record versions and effective options in each JVM through the actual factory. Check the contract through that factory (SAT, UNSAT, scalar/array/FP model, detach, scopes, assumptions, core, time limits/seed) and a live Java smoke with known feasible and infeasible outcomes. Do not time held-out projects before the gate. Old experiment 17 may be used solely for calibration if needed. If JNI fails by approximately 90 minutes from 14:52:43 MSK, use only a validated matched cvc5 1.4.1 live fallback within the time bound, identify Z3 transport, and label any old-version result as supplementary. Hard wall deadline 19:52:43 MSK; reserve at least 10 minutes to close and report. Limit to cores 12–15 (four distinct physical cores), one JVM per core; workspace below 12 GB; no external writes other than transient caches.

## Population and assignment

Ten locally installed public JAR families across regex (re2j, automaton), text/validation (jsoup, commons-validator, packageurl-java), collections/bitmap (hppc, RoaringBitmap), search utilities (lucene-core), compression (lz4-java), and reflection (generics-resolver). Project split is completely disjoint from overnight/campaign library admissions; check earlier manifests and exact class/method overlap automatically before running. Synthetic smoke belongs to engineering only. Exact JAR versions, include namespaces, SHA-256 and frozen method list go in inputs/manifest.json. Static selection only, via ASM. Select public concrete methods with parameters and 1+ conditional/switch instructions, no native or abstract, constructors, generated bridges, or synthetic methods. Require 8–260 real bytecode instructions. Disallow overlapping classes within project and select 4 methods with 1–2 and 4 with 3+ static decision instructions using SHA-256 ordering with salt live141-holdout-v1, taking available strata and filling by salted hash if deficient. Select no method on the basis of any SAT result, performance or coverage. Record scope and eligible counts. Classfile versions should work with Java 21. Keep selected methods even on error.

One project by one repeat is a paired block (8 methods × 3 arms). Six repeats, all six arm permutations once per project in independently seeded random order (schedule seed 1410526). Randomize method order per block, shared across its three arms, and shuffle block order; assign same core to all 3 arms sequentially, spread project repeats across cores and balance total lane load. Common JVM image, Java 21, 2 GiB heap with SerialGC, one available processor, fixed locale/timezone and configuration; each arm fresh JVM. Index project and a tiny synthetic warmup shared across arms; run fixed warmup sequence with that arm before measured methods. Separate app indexing, warmup and external wall time (JVM launch to exit, with setup) from main measured batch wall (all target methods in one JVM including solver creation, model work, and teardown), as well as per-method wall for construction+analysis+close. Keep per-method order/logs. JVM cap 150 s including startup (RSS guard 3.2 GiB per JVM), no hidden in-client total cutoff. Same FORK_DEPTH, seed 0 (path selection and native default random seed 0 where applicable), transitive coverage, 6 s exploration guard, 1.6 s per solver check and 1 s type-operation guard, 4000 maximum steps, 3500 steps since last collected state, original stop-on-100% and state-collection settings. Stop on visible interpreter exception in every arm. Class initialization, missing models/approximations and other states remain in scope. Record exact stop reason (queue exhausted, coverage goal, step/stagnation caps, exploration timeout) and unknown reasons, distinguish method vs outer timeout and number started/emitted.

## Outcomes and interpretation

Primary time estimand: arithmetic mean per intended method with PAR2-style penalty: observed machine end-to-end time for successful budget completion (queue exhausted, coverage target or deterministic step budget), 2×8 s for method time stop, unexplained error or outer-censored/missing method. Sensitivity at 1× and 3×8 s, and conditional paired times for each outcome subset, with denominators. Report external wall for every scheduled JVM (with outer cap and errors visible) and batch time without startup as separate diagnostics. Coverage co-outcomes: transitive instruction coverage, entry-method distinct conditional/switch successor edges, collected states, terminated paths and observed steps; unique target method signatures, returned results and completed analyses. Coverage on jointly observed methods plus missing-as-zero sensitivity and method-level discordances. Disaggregate solver SAT/UNSAT/UNKNOWN (timeout reason), check counts/time and model/solver setup share; count integration failures. When a setting changes the search performed, investigate common differing methods and do not infer equal-work acceleration from time alone. Flag material changes: >2 pp in mean instruction coverage, >5% aggregate branch edges or terminated paths, >2 pp in timeouts/errors/completion, or strong method-local shifts despite an equal aggregate. Compare none vs default first, each vs Z3 descriptively. Project-cluster bootstrap, resampling complete projects with all their methods/paired repeats, seed 504141, 10,000 draws, 95% percentile intervals, ratios of pooled means and paired mean differences; show leave-one-project-out sensitivity and project estimates. No extrapolation to all Java workloads. Verification reruns analysis from frozen schedule and raw outputs independently and checks JNI, order, count, durations and coverage invariants.

Only infrastructure failure may trigger a clearly labeled whole-block rerun, with all logs retained and the initial assignment staying in primary analysis unless pre-data integration failure invalidated the entire attempt. Report all timestamps MSK, including engineering failures and retries. Stop without substituting arms if the pinned/version gate fails. Deviations must be recorded before holdout execution when practical.
