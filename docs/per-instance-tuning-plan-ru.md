# План per-instance тюнинга cvc5 для TSA, версия 0

## Цель

Проверить, можно ли по короткому профилю конкретной TSA-нагрузки подобрать
новую конфигурацию cvc5, которая ускоряет последующий полный запуск этой
нагрузки и окупает стоимость профилирования и поиска.

Главная идея эксперимента — именно **тюнинг**, а не выбор одного из нескольких
заранее подготовленных preset-конфигураций. Для каждого workload тюнер может
собрать собственную комбинацию параметров из разрешённого пространства.

На первом этапе основной алгоритм поиска — SMAC или эквивалентный
tree-based Bayesian optimization. Random Search и категориальная эволюционная
стратегия нужны как baselines, чтобы измерить пользу интеллектуального поиска.

## Что именно мы хотим доказать

Эксперимент должен отдельно ответить на три вопроса.

1. **Тюнингуем ли cvc5 вообще?** Существуют ли для реалистичных TSA-нагрузок
   допустимые конфигурации, которые стабильно лучше конфигурации по умолчанию?
2. **Помогает ли интеллектуальный поиск?** Находит ли SMAC хорошие
   конфигурации быстрее или чаще, чем Random Search и ES при одинаковом
   бюджете?
3. **Можно ли предсказывать результат тюнинга?** Может ли модель по короткому
   профилю нового workload сразу предложить собственную конфигурацию, близкую
   к результату дорогого offline-тюнинга?

Положительный ответ на первый вопрос не доказывает второй, а положительный
ответ на первые два не доказывает обобщение модели. Поэтому эти результаты не
следует смешивать в одной метрике.

## Основные понятия

- **Workload** — одна независимая задача анализа: контракт, метод, набор
  входных параметров и seed TSA.
- **Профиль** — записанная последовательность операций над solver вместе с AST,
  результатами и длительностями.
- **Параметрическое пространство** — разрешённые параметры cvc5, их типы,
  диапазоны, условия применимости и ограничения совместимости.
- **Кандидат** — одна конкретная комбинация значений параметров cvc5.
- **Evaluator** — компонент, который реально запускает кандидата и возвращает
  время, статусы, timeout и ошибки.
- **Тюнер** — алгоритм, который выбирает, какого кандидата передать evaluator’у
  следующим.
- **Incumbent** — лучшая корректная конфигурация, найденная к текущему моменту.
- **Tuning budget** — ограничение на суммарное время и/или число реальных
  запусков evaluator’а.
- **Surrogate** — дешёвая модель внутри тюнера, приближённо предсказывающая
  результат ещё не проверенной конфигурации.

## Почему это не выбор готовых конфигураций

В основном эксперименте не должно быть фиксированного списка вроде
`default`, `fast`, `aggressive`, из которого выбирается один элемент.

SMAC работает иначе:

```text
разрешённые значения параметров cvc5
                |
                v
несколько реально измеренных кандидатов
                |
                v
Random Forest учит зависимость
    configuration -> cost/status
                |
                v
SMAC строит новую комбинацию параметров
                |
                v
реальный evaluator проверяет её на cvc5
                |
                +------ результат возвращается в Random Forest
```

Таким образом, дерево не заменяет solver и не выдаёт ответ на основании
заводских preset’ов. Оно помогает не расходовать дорогой бюджет на заведомо
неперспективные области пространства. Каждый новый кандидат всё равно
проверяется настоящим cvc5.

Готовые конфигурации допустимы только в качестве сравнительных точек:

- стандартная конфигурация cvc5;
- лучший единый кандидат, найденный только на development-нагрузках;
- случайный поиск с тем же бюджетом;
- ES с тем же бюджетом.

Они не ограничивают область поиска SMAC и не являются production-решением.

## Как будет работать один цикл тюнинга

### 1. Получение репрезентативного профиля

TSA запускается с конфигурацией cvc5 по умолчанию на ограниченное время.
Профилировщик записывает завершённый префикс solver-сессии:

- assertions и assumptions;
- `push` и `pop`;
- `check` и его timeout;
- SAT/UNSAT/UNKNOWN;
- обращения к model и unsat core;
- AST, необходимые для точного replay;
- контекст workload, версии и provenance.

Префикс должен завершаться в корректной точке, например после законченного
`check`. Простое обрезание JSON по времени недопустимо: оно может оставить
незакрытую операцию или нарушить порядок solver-событий.

### 2. Построение пространства поиска

Для зафиксированной версии cvc5 создаётся конкретный
`cvc5-parameter-space-v0`:

- булевы параметры;
- категориальные параметры;
- небольшие целочисленные диапазоны;
- условные зависимости;
- запрещённые комбинации;
- параметры, которыми владеет evaluator и которые тюнер менять не может.

Полный каталог не урезается заранее: для cvc5 1.3.4 он содержит 518
канонических опций. Конкретный эксперимент получает широкое, но условное
пространство: активны только теоретические модули, встречающиеся в workload,
а lifecycle-, I/O- и resource-policy опции принадлежат evaluator'у. Это не
ручной выбор «хороших готовых конфигураций»: search по-прежнему собирает новые
комбинации значений. Причина исключения каждой опции должна быть явной и
машиночитаемой.

Полная инвентаризация по модулям, количества и вопросы для валидации описаны в
[`cvc5-1.3.4-option-space-review-ru.md`](cvc5-1.3.4-option-space-review-ru.md).

### 3. Начальные измерения

Перед поиском evaluator измеряет:

1. конфигурацию cvc5 по умолчанию;
2. несколько случайных допустимых кандидатов;
3. при необходимости несколько локальных мутаций default-конфигурации.

Это даёт surrogate первые наблюдения и одновременно проверяет, что пространство
параметров и correctness gate работают.

### 4. Итерации SMAC

На каждой итерации:

1. Random Forest получает историю вида
   `(configuration, measured cost, status, timeout)`;
2. оценивает ещё не проверенные области пространства;
3. acquisition-функция выбирает перспективную новую конфигурацию;
4. replay evaluator запускает настоящий cvc5;
5. некорректный ответ, crash или invalid option фиксируется как неуспех;
6. timeout получает заранее определённый штраф;
7. корректное измерение добавляется в историю;
8. incumbent обновляется только при подтверждённом улучшении.

Поиск прекращается по первому достигнутому ограничению:

- исчерпан wall-clock budget;
- исчерпан evaluation budget;
- слишком долго нет улучшений;
- внешний эксперимент отменён.

### 5. Подтверждение финалистов

Шумное единичное измерение не должно становиться победителем. Несколько лучших
кандидатов повторно запускаются:

- в свежих solver;
- по возможности в отдельных JVM;
- в рандомизированном порядке вместе с default;
- с одинаковым числом повторений;
- при одинаковой политике CPU и фоновой нагрузки.

Сравнивается медиана, а для итогового отчёта строится доверительный интервал
парного относительного ускорения.

### 6. Полная end-to-end проверка

Лучший кандидат replay-поиска передаётся не обратно в сохранённый профиль, а в
новый полный запуск TSA:

```text
контракт
    -> новый процесс TSA
    -> новая интерпретация
    -> fresh cvc5 с найденными параметрами
    -> полный результат анализа
```

Только эта стадия позволяет утверждать, что ускорилась задача пользователя, а
не только фиксированная последовательность SMT-запросов.

## Протокол 10/90

### Строгий вариант для одного запуска

Пусть `B` — одинаковый общий бюджет для baseline и тюнингуемого метода.

```text
Baseline:
    default TSA                          <= B

Tuned:
    сбор профиля + поиск конфигурации    <= 0.1 B
    финальный запуск TSA                 <= 0.9 B
```

Это честная постановка, если стоимость каждого replay-кандидата входит в первые
10%. Нельзя бесплатно выполнить десятки конфигураций, а затем учитывать только
время выбранной.

Если полный default-запуск занимает `T0`, а профилирование и поиск стоят
`0.1 * T0`, итоговый tuned-запуск должен занять меньше `0.9 * T0`, чтобы метод
вообще окупился. Это соответствует ускорению основного запуска больше чем
примерно `1.11x`.

Практическая проблема: один полный replay может сам занимать существенную долю
`B`. Поэтому поиск должен быть многоступенчатым:

```text
много кандидатов   -> короткий replay-префикс
лучшие кандидаты   -> более длинный префикс
2-3 финалиста      -> полный replay
1 победитель       -> полный запуск TSA
```

Кандидат, отброшенный на короткой стадии, больше не расходует полный бюджет.
При этом aggressive capping должен сравнивать кандидатов на одинаковом объёме
нагрузки и не использовать будущую test-информацию.

### Амортизируемый вариант

Если одна конфигурация применяется к нескольким похожим запускам, сравнивается:

```text
tuning_cost + sum(tuned end-to-end runtimes)
```

с:

```text
sum(default end-to-end runtimes)
```

Этот вариант практичнее, но требует заранее определить, что означает
«похожие»: один контракт с разными seed, разные методы одного проекта или
контракты одного семейства. Менять определение после получения результатов
нельзя.

### Offline-вариант для подготовки модели

При генерации обучающего датасета поиск может быть значительно дороже 10%.
Этот расход считается offline training cost и не скрывается, но не входит во
время production inference. На невиданном test-workload выполняются только:

```text
короткое профилирование
    -> один inference модели
    -> свежий запуск с предсказанной конфигурацией
```

Это отдельное утверждение об обобщении модели, а не тот же эксперимент, что
per-instance SMAC.

## Внутренняя и внешняя метрики

### Внутренняя метрика поиска

Replay evaluator использует быстрый и воспроизводимый proxy:

```text
cost = non-check solver time
     + time of checks with known SAT/UNSAT status
     + timeout penalties
```

Кандидат получает hard failure при:

- противоположном SAT/UNSAT результате;
- падении replay;
- недопустимой опции;
- неполном профиле.

Эта метрика помогает тюнеру, но не является финальным доказательством.

### Основная итоговая метрика

Для завершающейся задачи:

```text
total tuned cost = profiling + tuning + final TSA wall time
```

Для анализа с жёстким deadline:

1. отсутствие correctness-регрессий;
2. количество полностью проанализированных целей;
3. coverage;
4. число обработанных состояний или запросов;
5. найденные ошибки;
6. solver time как диагностическая метрика.

Итоговый отчёт также показывает отдельно:

- время профилирования;
- время поиска;
- число реально проверенных кандидатов;
- время финального запуска;
- replay speedup;
- end-to-end speedup;
- timeout, crash и invalid configuration;
- медиану и разброс по повторениям.

## Алгоритмы, которые сравниваются

Бейзлайны делятся на четыре группы, потому что отвечают на разные вопросы.

| Группа | Бейзлайны | Что проверяем |
|---|---|---|
| Конфигурации | default, best fixed на development, oracle best observed | Нужна ли адаптация под workload и какой наблюдался верхний предел |
| Алгоритмы поиска | Random Search, ES/CEM, SMAC без и с multi-fidelity | Помогают ли surrogate и staged evaluation при равном бюджете |
| Обученный тюнер | default, best fixed, детерминированная эвристика, ML predictor, SMAC oracle | Даёт ли модель пользу сверх статической и простой адаптации |
| Полная система | default TSA против `profile + tune/infer + fresh TSA` | Окупается ли настройка end-to-end |

`Best fixed` выбирается только на development workloads. Он нужен не как
предлагаемое решение, а чтобы проверить, действительно ли индивидуальная
настройка полезнее одной удачной общей конфигурации. `Oracle best observed`
выбирается post hoc отдельно для каждого workload и никогда не считается
доступной production-системой.

Для Random Search, ES/CEM и SMAC одинаковы parameter space, ограничения,
evaluator, correctness gate, wall-clock budget и правила подтверждения
финалистов. Одинаковое число evaluations показывается дополнительно, но не
заменяет равенство фактически потраченного времени.

### Default cvc5

Обязательная нулевая точка. Она не участвует в обучении и не получает
дополнительный бесплатный бюджет.

### Random Search

Обязательный baseline для алгоритма поиска. Он независимо мутирует параметры
относительно default-конфигурации с явно зафиксированной вероятностью, проверяет
допустимость и сохраняет лучшую. Такая prior не удаляет ни одной конфигурации из
пространства, но не тратит почти весь бюджет на одновременную случайную смену
десятков сильно взаимодействующих параметров. Если SMAC не превосходит Random
Search при том же бюджете и согласованной default-centred prior, усложнение не
оправдано.

### Категориальная ES или Cross-Entropy Method

Нужна как проверка исходной гипотезы. Алгоритм поддерживает распределение по
значениям параметров, генерирует population и сдвигает вероятности к лучшим
кандидатам. Для смешанного пространства это корректнее, чем Gaussian ES над
искусственно закодированными числами.

### SMAC

Основной кандидат. Он использует измерения evaluator’а, Random Forest и
acquisition policy, чтобы выбирать новые комбинации параметров. Его преимущество
должно подтверждаться не названием алгоритма, а сравнением с Random Search и ES
при одинаковом wall-clock и evaluation budget.

### TPE или irace

Резервные методы. Они полезны, если интеграция SMAC окажется чрезмерно сложной
или его модель плохо работает на фактическом пространстве параметров. Не нужно
реализовывать все методы до первого пилота.

## Как из тюнинга получится модель

Каждый запуск SMAC создаёт не только одну метку «лучшая конфигурация», но и
полезную историю:

```text
profile features
configuration
measured cost
status
timeout/crash
evaluation budget
```

Эту историю следует сохранять как основной обучающий материал. Она позволяет
учить два типа моделей.

### Inference-only модель текущей архитектуры

Модель получает признаки профиля и выдаёт значения параметров, образующие новую
конфигурацию. Это не выбор заводского preset. Target для обучения получается из
per-workload тюнинга SMAC.

```text
profile features
    -> model
    -> custom cvc5 parameter values
    -> validation and fallback
```

Такой вариант совместим с текущей границей `ksmt-ml-tuner`: в production нет
replay и runtime-поиска.

### Learned surrogate с runtime-поиском

Более сильный, но архитектурно более сложный вариант моделирует:

```text
(profile features, configuration) -> predicted cost/status
```

Затем дешёвый оптимизатор перебирает значения уже по предсказаниям модели, а
не запускает cvc5 для каждого кандидата. Если же модель дополнительно проверяет
кандидатов на реальной задаче, это становится online-тюнингом и требует новых
контрактов budget, cancellation, persistence и solver isolation.

Этот вариант следует рассматривать после inference-only MVP, а не смешивать с
первым экспериментом.

## Что уже есть

1. KSMT-профиль инкрементальной solver-сессии.
2. TSA-адаптер, записывающий replayable AST и события cvc5.
3. Replay evaluator, создающий fresh `KCvc5Solver` и реально повторяющий
   операции профиля.
4. Проверка известных SAT/UNSAT результатов.
5. Учёт timeout, падений и неуспешных событий.
6. Сравнение кандидата с кешированным default baseline.
7. Reward на основе log-speedup по workload.
8. v0-схемы кандидата, replay-отчёта и score.

Этого достаточно для ручной проверки нескольких конфигураций и для подключения
первого search algorithm, но недостаточно для доказательного 10/90
эксперимента.

## Каких больших частей не хватает

### 1. Реальное пространство параметров cvc5

Сейчас есть формат пространства, но нет зафиксированного набора безопасных
опций для конкретной версии cvc5. Нужны домены, ограничения, значения по
умолчанию и тест каждой разрешённой комбинации на корректность конфигурации.

### 2. Search orchestrator

Нужен общий цикл `ask -> evaluate -> tell`, который:

- подключает Random Search, ES и SMAC к одному evaluator;
- соблюдает wall-clock и evaluation budget;
- дедуплицирует кандидатов;
- кеширует результаты;
- сохраняет checkpoint;
- продолжает эксперимент после остановки;
- фиксирует seed и всю provenance.

### 3. Многоступенчатая оценка

Нужны короткие, средние и полные replay-наборы, successive halving и
aggressive capping. Без этого один плохой кандидат может занять часы, а строгий
10% tuning budget окажется практически недостижим.

### 4. Корректные временные префиксы профиля

Нужно уметь завершать сбор после заданного времени или числа `check`, сохраняя
валидную solver-сессию. Обычная обрезка уже собранного JSON недостаточна.

### 5. End-to-end TSA evaluator

Нужен runner, который принимает контракт и candidate, запускает TSA с нуля и
записывает:

- wall time;
- timeout и exit status;
- coverage;
- число состояний и solver checks;
- найденные ошибки;
- итоговую cvc5-конфигурацию;
- версии и host provenance.

Он должен использовать те же правила process isolation, repetitions и
correctness gate, что replay evaluator.

### 6. Correctness oracle уровня TSA

Совпадения SAT/UNSAT в replay недостаточно. Нужна политика сравнения полного
анализа: какие результаты обязаны совпасть, какие изменения coverage допустимы
и как трактуются UNKNOWN и timeout.

### 7. Feature extractor

Нужна стабильная векторная проекция профиля. Она должна одинаково работать в
Python при обучении и в JVM при production inference. До её появления можно
тюнить одну нагрузку, но нельзя честно обучать `profile -> configuration`.

### 8. Набор независимых workload

Один контракт позволяет доказать только per-instance tunability. Для модели
нужны разные контракты и семейства, разделённые по группам. Запуски одного
контракта нельзя случайно разнести между train и test как независимые примеры.

### 9. Experiment store и статистический отчёт

Нужно хранить каждый запуск, включая неуспешные, и автоматически строить:

- learning curve «лучший результат против потраченного бюджета»;
- число timeout/crash/wrong answer;
- распределение speedup;
- paired bootstrap confidence interval;
- сравнение Random Search, ES и SMAC по нескольким seeds;
- полную стоимость tuning + final run.

### 10. Реальная проверка версии solver

Replay-отчёт должен фиксировать версию фактически загруженного cvc5, а не только
версию, записанную в исходном профиле.

## Поэтапный план реализации

### Этап 0. Зафиксировать постановку

- выбрать одну версию cvc5;
- выбрать определение workload;
- выбрать строгий или амортизируемый бюджет;
- определить primary end-to-end metric;
- зафиксировать correctness gate;
- определить единицу независимого train/test split.

Результат: `experiment-manifest-v0` без данных будущего эксперимента.

### Этап 1. Подготовить пространство параметров

- выбрать небольшой набор параметров;
- описать домены и зависимости;
- запретить evaluator-controlled options;
- добавить constraint validation;
- выполнить smoke-проверку значений на реальном cvc5.

Результат: конкретный `cvc5-parameter-space-v0`.

### Этап 2. Реализовать общий search loop

- определить интерфейс стратегии `ask/tell`;
- реализовать Random Search;
- добавить кеш и дедупликацию;
- добавить checkpoint/resume;
- добавить wall-clock и evaluation budget;
- сохранять полный trace поиска.

Результат: воспроизводимый random-search pilot.

### Этап 3. Сделать replay достаточно дешёвым

- реализовать корректные profile prefixes;
- добавить staged evaluation;
- добавить per-candidate и per-stage timeout;
- повторно измерять только финалистов;
- изолировать финальные repetitions.

Результат: один поиск укладывается в заранее объявленный бюджет.

### Этап 4. Подключить SMAC

- преобразовать parameter space в формат SMAC/ConfigSpace;
- передавать измеренный cost и статус;
- корректно учитывать timeout и crash;
- сохранять историю и incumbent;
- не позволять SMAC видеть финальный test-run.

Результат: SMAC и Random Search работают через один evaluator.

### Этап 5. Добавить ES baseline

- использовать категориальные распределения;
- обрабатывать conditional parameters;
- дать тот же бюджет и те же candidate constraints;
- запустить несколько фиксированных seeds.

Результат: честное сравнение search algorithms.

### Этап 6. Реализовать end-to-end runner

- запускать TSA с кандидатом в свежем процессе;
- передавать настройки cvc5 до первых assertions;
- собирать результат анализа и системные метрики;
- проверять correctness;
- считать полную стоимость, включая tuning.

Результат: можно доказать или опровергнуть ускорение всей задачи.

### Этап 7. Провести одноконтрактный пилот

- выбрать один достаточно длинный стабильный контракт;
- измерить default;
- выполнить Random Search, ES и SMAC с одинаковыми бюджетами;
- перепроверить финалистов полным replay;
- выполнить новые полные TSA-запуски;
- опубликовать и положительный, и отрицательный результат.

Результат: доказательство per-instance tunability, но не качества модели.

### Этап 8. Расширить workload corpus

- собрать независимые контракты и семейства;
- заморозить grouped train/validation/test split;
- выполнять тюнинг отдельно на каждом development workload;
- сохранить полные traces, а не только победителей.

Результат: датасет для обучения модели.

### Этап 9. Обучить inference-only модель

- зафиксировать feature schema;
- начать с простых tree-based baselines;
- предсказывать собственные значения параметров, а не ID preset’а;
- валидировать и применять fallback;
- сравнить с default, best fixed, Random Search oracle и SMAC oracle;
- оценить только один раз на sealed workload groups.

Результат: кандидат на ONNX bundle или честный отрицательный вывод.

## Минимальный первый доказательный эксперимент

Первый результат можно считать содержательным, если одновременно выполнено:

1. используется настоящий cvc5;
2. Random Search, ES и SMAC получают одинаковый бюджет;
3. default не переизмеряется выборочно только в удобных условиях;
4. все timeout, crash и invalid candidates сохранены;
5. поиск не использует время финального test-run;
6. победитель подтверждён повторениями;
7. выполнен новый полный запуск TSA;
8. нет SAT/UNSAT и TSA-level correctness-регрессий;
9. указана полная стоимость профилирования и поиска;
10. результат воспроизводится по manifest, seed и версиям.

Если улучшение есть только на replay, вывод формулируется как «ускорен
solver-level replay». Если улучшился новый полный запуск TSA, можно говорить об
end-to-end ускорении. Если результат получен на одном контракте, нельзя
утверждать, что он переносится на другие контракты.

## Академическое обоснование

План опирается не на предположение, что «деревья должны сработать», а на
существующую область automatic algorithm configuration. При этом литература
подтверждает применимость общего метода, но не гарантирует ускорение именно
cvc5 на TSA. Последнее всё равно должно быть установлено экспериментально.

### SMAC и SMAC3

Исходная работа **Sequential Model-Based Optimization for General Algorithm
Configuration** формулирует тот же внешний цикл, который нужен проекту:
строить empirical performance model по уже измеренным конфигурациям, выбирать
перспективного challenger, реально запускать целевой алгоритм и повторять до
исчерпания бюджета. На странице проекта также отдельно перечислены работы про
time-bounded configuration, parallel configuration и Bayesian optimization с
censored runtime data.

- Hutter, Hoos, Leyton-Brown, *Sequential Model-Based Optimization for General
  Algorithm Configuration*, LION 2011:
  <https://www.cs.ubc.ca/labs/algorithms/Projects/SMAC/>

Современный SMAC3 — поддерживаемая Python-реализация этой идеи. Статья SMAC3
описывает её как Bayesian optimization framework в том числе для настройки
алгоритма на множестве problem instances. Это соответствует нашей роли
`evaluator(candidate, workload) -> cost/status`.

- Lindauer et al., *SMAC3: A Versatile Bayesian Optimization Package for
  Hyperparameter Optimization*, JMLR 2022:
  <https://www.jmlr.org/papers/v23/21-0888.html>

Документация SMAC3 подтверждает наличие нужных инженерных механизмов:

- категориальные, ordinal, числовые и условные параметры;
- ask-and-tell API;
- запуск внешнего target function через script;
- warm start и продолжение run history;
- instances, seeds и budgets;
- intensification;
- параллельные trials;
- multi-fidelity optimization.

Источник: <https://automl.github.io/SMAC3/latest/>

Следовательно, отдельный самописный Random Forest optimizer проекту не нужен.
Наша работа состоит в корректном адаптере между SMAC3 и evaluator, а также в
научно честном определении workload, cost, budget и correctness gate.

### Multi-fidelity и intensification

SMAC3 поддерживает Successive Halving и Hyperband: сначала кандидаты получают
малый бюджет, после чего только лучшие переходят на более дорогие fidelity.
Это прямо соответствует предложенной последовательности
`короткий prefix -> средний prefix -> полный replay`.

- SMAC3, *Multi-Fidelity Optimization*:
  <https://automl.github.io/SMAC3/v2.0.1/advanced_usage/2_multi_fidelity.html>
- SMAC3, *Components and Intensifier*:
  <https://automl.github.io/SMAC3/main/advanced_usage/1_components/>

Однако применимость multi-fidelity требует дополнительного свойства: дешёвая
fidelity должна быть информативна о дорогой. В нашем случае нельзя заранее
считать, что первые 5% solver-сессии хорошо предсказывают полный запуск.
Поэтому до включения Successive Halving необходимо измерить:

- Spearman или Kendall correlation между short и full cost;
- top-k recall: сколько полных победителей переживает короткий отбор;
- долю конфигураций, меняющих знак speedup между prefix и full replay;
- стабильность этих значений между workload groups.

Если корреляция мала, временной префикс нельзя использовать как fidelity.
Тогда дешёвая стадия должна строиться иначе: например, на стратифицированной
выборке checks, наборе representative shards или меньшем числе workload
instances.

### Adaptive capping и racing

ParamILS — классическая работа по automatic algorithm configuration —
оценивает конфигурации реальными запусками целевого алгоритма и использует
ограниченные cutoff times. Связанные работы SMAC развивают adaptive capping и
работу с censored runtimes. Это поддерживает наше требование рано останавливать
явно плохого кандидата и не ждать бесконечного solver timeout.

- Hutter, Hoos, Leyton-Brown, Stützle, *ParamILS: An Automatic Algorithm
  Configuration Framework*, JAIR 2009:
  <https://www.cs.ubc.ca/labs/algorithms/Projects/MIP-Config/papers/09-JAIR-ParamILS.pdf>

Практическая деталь: timeout нельзя терять после преобразования в одно число.
Experiment store должен одновременно сохранять:

- фактически измеренное время;
- cutoff;
- признак censoring/timeout;
- PAR-штраф, использованный в целевой функции.

Это позволит передать SMAC корректный trial status и позднее изменить
штрафную политику без потери исходных наблюдений.

### Настройка сложных solver

Работы по ParamILS и SMAC были проверены не только на ML-гиперпараметрах, но и
на SAT, MIP и других сложных алгоритмах с большим числом взаимодействующих
параметров. Авторы configuration-подхода отдельно демонстрировали автоматическую
настройку CPLEX, Gurobi и других MIP-solvers; на странице проекта сообщаются
существенные ускорения на отдельных классах instances.

- Hutter, Hoos, Leyton-Brown, *Automated Configuration of Mixed Integer
  Programming Solvers* и материалы проекта:
  <https://www.cs.ubc.ca/labs/algorithms/Projects/MIP-Config/>

Это не является доказательством будущего ускорения cvc5. Но это подтверждает,
что black-box tuning реального solver с категориальными параметрами, timeout и
дорогими запусками — стандартная и реализуемая экспериментальная постановка.

## Дополнения к плану по результатам литературы

### 1. Разделить два режима SMAC3

Для одного workload используется отдельный per-instance search:

```text
configuration -> replay одного workload -> cost
```

Для поиска конфигурации на распределении development-workloads используется
algorithm-configuration scenario:

```text
configuration + instance -> replay -> cost
```

Во втором режиме SMAC должен получать идентификаторы instances и, когда
доступно, их признаки. Нельзя просто склеить все solver checks в один большой
профиль: тогда большие workloads начнут неявно иметь больший вес.

### 2. Передавать SMAC cost, а не reward

SMAC3 минимизирует target function. Наш внешний score с
`log(default_cost / candidate_cost)` максимизируется и удобен для отчёта, но
адаптеру SMAC лучше возвращать непосредственно нормализованный cost:

```text
optimization_cost = candidate_effective_cost / default_effective_cost
```

или его логарифм:

```text
optimization_cost = log(candidate_effective_cost / default_effective_cost)
```

Статусы timeout, crash и memory-out передаются отдельно, а не маскируются
обычным числом. Внешний reward остаётся отчётной метрикой и не меняет знак
внутри интеграции несколько раз.

### 3. Измерять качество самого configurator

Сравнивается не только одна итоговая конфигурация, но и весь алгоритм поиска.
Для Random Search, ES и SMAC нужно показать:

- incumbent cost против потраченного wall-clock;
- incumbent cost против числа solver evaluations;
- area under the anytime curve;
- вероятность найти улучшение заданного размера;
- результат в конце одинакового бюджета;
- разброс по независимым seeds самого configurator.

Это предотвращает выбор удачного единичного запуска SMAC.

### 4. Проверить перенос replay -> TSA

Для набора кандидатов, а не только для одного победителя, следует измерить и
replay cost, и end-to-end TSA cost. Затем вычислить:

- корреляцию рангов;
- top-k recall;
- долю ложных победителей replay;
- долю конфигураций с изменившимся correctness/coverage результатом.

Если replay не сохраняет ранжирование, его нельзя использовать как основной
black-box objective. Тогда часть end-to-end запусков должна войти в tuning loop
или replay objective должен быть изменён.

### 5. Не фиксировать 10% без development-исследования

Доля 10/90 понятна как первая гипотеза, но научно лучше построить budget curve:

```text
1/99, 3/97, 5/95, 10/90, 20/80
```

Доля выбирается только на development workload groups. На test-группе она уже
не меняется. Это покажет точку, после которой дополнительные измерения тюнера
перестают окупаться.

### 6. Зафиксировать два уровня бюджета

Нужно одновременно ограничивать:

- число trial evaluations — для сравнения sample efficiency;
- фактический wall-clock — для практической окупаемости.

Одинаковое число trials не является одинаковой стоимостью, потому что плохие
конфигурации могут работать значительно дольше. В строгом 10/90 эксперименте
основным ограничением является wall-clock, а evaluation count остаётся
диагностической метрикой.

### 7. Добавить ablation study

Чтобы понять, откуда возникает улучшение, нужны отдельные варианты:

- Random Search;
- SMAC без multi-fidelity;
- SMAC с multi-fidelity;
- SMAC без profile/instance features;
- SMAC с profile/instance features;
- ES/CEM;
- default cvc5.

Это отделит пользу Random Forest от пользы early stopping, warm start и
правильно выбранного parameter space.

### 8. Сделать два последовательных MVP

**MVP-A: доказать tunability.** Один или несколько workloads, SMAC создаёт
новые конфигурации, победители проходят full replay и end-to-end TSA.

**MVP-B: доказать generalization.** SMAC-трассы на development workloads
становятся датасетом; модель по короткому профилю предсказывает собственные
значения параметров; результат проверяется на sealed workload groups.

Такой порядок не позволяет неудачной модели скрыть более фундаментальный
результат: возможно, выбранное пространство cvc5 вообще не даёт устойчивого
ускорения для TSA.

## Итог академической проверки

Литература поддерживает следующие части плана:

- реальная black-box настройка алгоритма вместо выбора preset’а;
- Random Forest surrogate для смешанных и условных параметров;
- последовательный выбор challenger-конфигураций;
- time-bounded configuration;
- явная обработка timeout/censored runs;
- intensification по instances и seeds;
- Successive Halving/Hyperband при наличии валидной дешёвой fidelity;
- сравнение configurators при одинаковом бюджете.

Литература не подтверждает автоматически две специфические гипотезы проекта:

1. короткий профиль TSA предсказывает лучшую конфигурацию для полного профиля;
2. ускорение solver replay переносится в end-to-end ускорение TSA.

Эти две гипотезы становятся обязательными промежуточными экспериментами. Если
они подтверждаются, весь последующий путь к SMAC-generated labels и
inference-only модели имеет обоснованную экспериментальную основу.
